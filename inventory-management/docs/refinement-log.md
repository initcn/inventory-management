# OOAD Model Refinement Change Log
## Inventory & Multi-Warehouse Management System

This document records the systematic Object-Oriented Analysis and Design (OOAD) model refinements applied to transform the **Initial Class Model** (`02_InitialClassDiagram`) into the **Refined Class Model** (`03_RefinedClassDiagram`), demonstrating:
1. **Splitting classes** with mixed responsibilities.
2. **Combining classes** that represent stages of the same lifecycle.
3. **Eliminating unnecessary classes** that duplicate derived state.
4. **Making the model homogeneous** across all transactional inventory documents.
5. **Improving associations, multiplicities, and referential constraints**.

---

### Model Refinement Change Log Table

| # | Refinement Category | Initial Design | Refined Design | Reason for Refinement | Engineering & OOAD Benefit |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1** | **Splitting Classes** | Single monolithic `BatchInventory` class storing `batch_number`, `mfg_date`, `expiry_date`, `unit_cost`, `receipt_date`, `warehouse_id`, and `remaining_qty`. | Split into two distinct classes:<br>1. `Batch` (`id`, `batch_number`, `product_id`, `supplier_id`, `mfg_date`, `expiry_date`, `unit_cost`, `receipt_date`, `initial_quantity`)<br>2. `InventoryHolding` (`id`, `warehouse_id`, `batch_id`, `product_id`, `quantity`) | In a multi-warehouse system, transferring part of a batch from Warehouse A to Warehouse B means the same batch now exists in two warehouses. A monolithic class forced duplicating `unit_cost`, `expiry_date`, and `receipt_date` per warehouse. | Preserves Third Normal Form (3NF) and single source of truth for batch cost/expiry/receipt date while allowing any batch to be distributed across $N$ warehouses via `UNIQUE(warehouse_id, batch_id)`. |
| **2** | **Combining Classes** | Two separate classes `InternalDispatchNote` (outbound from source warehouse) and `InternalReceiptNote` (inbound at destination warehouse). | Combined into a single stateful `StockTransfer` (`transfers` + `transfer_items`) class with lifecycle states (`Draft` $\rightarrow$ `Dispatched` $\rightarrow$ `Partially Received` $\rightarrow$ `Received` / `Cancelled`). | Having separate dispatch and receipt classes made it possible to create an inbound receipt without a matching outbound dispatch or lose track of in-transit quantities. | Guarantees strict conservation of stock during inter-warehouse transfers and tracks `quantity` vs. `received_quantity` (`in_transit_quantity`) in a single cohesive aggregate. |
| **3** | **Eliminating Unnecessary Classes** | Persistent `LowStockAlert` and `ExpiredBatchAlert` entity classes stored in the database and manually toggled when stock changed. | Eliminated both persistent alert classes; replaced with dynamic query operations `ReorderService.check_reorder_levels()` and `InventoryService.get_expiry_alerts()`. | Stored alert tables easily become stale whenever time passes (`CURRENT_DATE` crosses `expiry_date`) or when goods receipts/adjustments occur. | Eliminates synchronization bugs and redundant database writes; expiry and reorder statuses are always 100% accurate relative to current stock and current date. |
| **4** | **Splitting Classes (Header–Line Decomposition)** | Flat `PurchaseOrder`, `GoodsReceipt`, `FifoStockIssue`, and `SupplierReturn` classes that embedded a single `product_id` and `quantity` directly on the header. | Split each transactional document into a **Header + Line Item** composition:<br>- `PurchaseOrder` (1) $\rightarrow$ (1..* ) `PurchaseOrderItem`<br>- `GoodsReceipt` (1) $\rightarrow$ (1..* ) `GoodsReceiptItem`<br>- `StockIssue` (1) $\rightarrow$ (1..* ) `StockIssueItem`<br>- `SupplierReturn` (1) $\rightarrow$ (1..* ) `SupplierReturnItem` | A single FIFO stock issue of 60 units often consumes from 2+ batches at different unit costs, and a single PO from a supplier can cover multiple products or receive multiple partial GRNs. | Enables multi-batch FIFO consumption breakdowns (`StockIssueItem`), multi-product supplier POs, and partial goods receipts linked to exact `po_item_id` and `batch_id` records. |
| **5** | **Making the Model Homogeneous** | Inconsistent attribute naming and audit logging across operations (`StockLogEntry` used free-text `actionDescription`, and document numbers had inconsistent formats). | Standardized all document headers (`po_number`, `grn_number`, `transfer_number`, `issue_number`, `return_number`) and unified all stock mutations through `StockTransaction` (`product_id`, `batch_id`, `warehouse_id`, `transaction_type`, `quantity`, `unit_cost`, `reference_type`, `reference_id`). | Free-text logs could not be reconciled mathematically against `inventory.quantity` or filtered reliably by warehouse/batch. | Every inventory change across all modules invokes the exact same `upsert_inventory_holding()` + `record_stock_transaction()` pair, guaranteeing that $\sum \text{StockTransactions} = \text{InventoryHolding.quantity}$. |
| **6** | **Refining Associations & Multiplicities** | Unconstrained dependency between `PurchaseOrder` and `ExternalSupplierClient` directly inside route handlers. | Introduced `SupplierIntegrationAdapter` in `integrations/supplier_adapter.py` invoked via `supplier_service.check_external_supplier_catalog()`. | Direct external calls in controllers violate layered architecture and make unit testing difficult when external services time out. | Isolates external communication behind the **Adapter Pattern**, allowing deterministic testing of `SUCCESS`, `FAILURE`, `TIMEOUT`, and `UNAVAILABLE` scenarios. |
